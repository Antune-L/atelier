# Automatic provider adoption

Provider adoption prepares a new application containing exact stable Claude and Codex dependencies. It does not replace global CLIs. Preparation does not reserve application maintenance. Installation requires a second explicit confirmation and waits for active native work to finish.

## Protected setup

Install `.github/workflows/provider-adoption.yml` on the default branch before enabling preparation. Create the GitHub environment `provider-adoption` and restrict its deployment branches to `main`. Environment approval rules apply to preparation, qualification and publication. Preparation checks out the immutable workflow commit, not an arbitrary supplied base; a base mismatch stops before dependency changes. Qualification has read-only repository permissions and does not persist checkout credentials; only candidate persistence and publication receive Contents write. The entire qualification job, including dependency installation and tests, runs under an account with provider credentials available. Restrict runner access and protect workflow edits accordingly.

Configure a dedicated backend token through `ATELIER_ADOPTION_TOKEN` or `ATELIER_ADOPTION_TOKEN_FILE`. Files should be readable only by the backend service account. Use a fine-grained token scoped only to `Antune-L/atelier`, with **Actions: write** for dispatch/status and **Contents: read** for source and release metadata. Local `gh`/project accounts are never used. GitHub's [workflow dispatch REST endpoint](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event) returns `workflow_run_id`, `run_url` and `html_url`. The request explicitly enables run details and persists the returned numeric identity. No latest-run selection is used.

Configure `ATELIER_ADOPTION_PUBLIC_KEY` or `ATELIER_ADOPTION_PUBLIC_KEY_FILE` with the trusted publisher Ed25519 public key. Preserve this key across upgrades. Configure the corresponding private PEM as the protected environment secret `ATELIER_UPDATE_SIGNING_KEY`. This authenticates the publisher; it is separate from Apple application signing. A missing signing key fails publication.

Qualification uses existing Claude and Codex subscription logins on dedicated self-hosted runners, not API-key secrets. Register a Linux x64 runner with labels `self-hosted`, `linux`, `x64`, `atelier-provider-adoption`, and an Apple Silicon macOS runner with labels `self-hosted`, `macOS`, `ARM64`, `atelier-provider-adoption`. GitHub routes jobs using the intersection of these [runner labels](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/use-in-a-workflow). Keep these runners dedicated to the trusted adoption workflow; do not share a production application account or run untrusted pull-request jobs with their provider profiles. Candidate code and dependency scripts can access the runner account's credentials.

Connect both providers under the operating-system account that runs each runner, using the normal Claude and Codex subscription sign-in flows. The existing account must have access to the qualification models, and macOS credential storage must be accessible to the runner process. Preserve the effective `HOME`, `CODEX_HOME` and `CLAUDE_CONFIG_DIR`; do not copy profiles into GitHub secrets or replace them with temporary homes. The qualification script does not invoke login/logout or replace authentication files; the providers may refresh their own cached sessions normally. It rejects `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` and `CODEX_API_KEY` environment variables to avoid silently qualifying through API billing; also ensure the existing Codex profile uses subscription authentication rather than a stored API key. See [Codex authentication](https://developers.openai.com/codex/auth). Provider calls consume the connected subscriptions' allowances and may require renewed sign-in. No credentials are requested through the browser or persisted in preparation records.

Once both runners are configured, set the repository Actions variable `ATELIER_ADOPTION_RUNNERS_READY` to `1`. An absent value fails preparation before candidate changes instead of queuing qualification on machines that were never configured. This is an operator readiness declaration, not a check that runners are online or logins are valid: offline runners still queue, and unavailable authentication fails real qualification. Preparation and publication continue to use GitHub-hosted runners without provider logins. Existing job and evidence names `ubuntu-latest` and `macos-15` remain stable identifiers for the Linux and macOS qualification outputs; qualification itself runs on the dedicated self-hosted machines.

The workflow uses its repository `GITHUB_TOKEN` with **Contents: write** to persist a candidate branch, fast-forward main and publish a release. Configure repository rules to permit this narrowly scoped automation, or promotion will fail explicitly. No branch-policy bypass is attempted. A token-created tag is not relied on to start another workflow: this workflow builds and publishes the complete Mac release itself.

## Qualification and provenance

SDK adoption and tariff review are separate policies. A validated SDK-only candidate retains the current local price grid; it does not claim current upstream prices or change the pricing verification date. New selectable models and tariff changes follow the separate procedure in [pricing.md](./pricing.md). Unknown models remain explicitly unpriced with partial totals. No tariff-review approval is required for an SDK-only candidate that preserves the product model list.

The candidate changes only `package.json`, `bun.lock` and the two native version constants. Preparation runs the existing known-model pricing regression; it does not claim to refresh upstream prices. Both Linux and macOS run existing typecheck, lint, full tests and the operational qualification runner from the candidate commit. The runner refuses native environment overrides and binaries outside the candidate installation. Real permission denial, interruption and native closure are required. Both providers must also recover a marker from persisted conversation history after closing the native session: Codex resumes its existing thread; Claude reconstructs a new session from the stored transcript. This supplements the existing native sessions, source/image hydration and session worker-tool scenarios; it is not a full backend process-death test.

Slot creation, repository/worktree changes and VCS effects in this runner remain simulated. Existing GitHub and Azure regression fixtures run in CI; no live GitHub/Azure PR mutation is claimed. Mac packaging is a real build, but this is not a live installation qualification of a deployed Mac or VPS.

Publication checks both persisted platform evidence files, exact source revision and lock hash, successful native contract coverage and cleanup. It signs `provider-adoption.json` and uses the same envelope as the versioned release body. The receipt binds the request, run, base, candidate, providers and complete artifact hashes. The backend additionally checks exact workflow identity and successful required jobs; missing or skipped gates never approve installation. An advanced main refuses promotion. No merge of unqualified changes occurs.

The initial automation uses the `0.1.<workflow run ID>` application release series. Before promotion it checks that this version advances the currently published application. A collision or a newer application release series blocks promotion instead of publishing a lower version as latest; evolve the version policy alongside the next application release series.

## Host activation

Source Mac uses the existing clean-main installer with explicit confirmation and a fresh comparison against the qualified revision. Its dependency installation uses the committed lock. If main advances, prepare a new candidate rather than installing an arbitrary SHA. Failed mutation retains the existing recovery barrier; code recovery does not restore databases or provider sessions.

Packaged Mac uses the existing publisher-authenticated complete application archive controller. An explicit signed `adoptionRunId` identifies an automated candidate; ordinary semantic versions are not treated as workflow IDs. A changed provider graph requires that marker and a matching receipt. The versioned manifest, candidate receipt, source graph and ZIP hash must agree. A Mac without the embedded trusted publisher key needs one manually installed trusted full release for first adoption. This does not export credentials or modify user configuration.

The VPS needs a one-time operator installation of the updated standalone `deploy/updater/updater.ts`. Add the trusted PEM public key as `adoptionPublicKey` in its root-owned `/etc/kanban-updater/config.json`, preserving its existing Cloudflare identity settings and permissions. When the target changes provider versions, the privileged updater verifies the signed latest qualification against the exact current main revision and lock before executing the existing immutable-release installer. Ordinary application updates retaining the installed provider graph keep their existing path. Both sidebar and provider confirmation dialogs resolve and display an exact target before starting. Existing root service hardening, attempt identifiers and failed/unknown recovery remain in force. No VPS operation is performed by this implementation task.

## Failure and recovery

Missing backend setup returns `setup-required`. Registry failures, workflow failures and publication failures leave the working installation active. Dispatch acknowledgement loss persists `unknown` before returning: a retry never blindly dispatches again. Status can recover only an exact unique request UUID and base match within the bounded workflow-run response; it never adopts another request's most recent run. If that exact execution is no longer in the bounded response, operator inspection is required. A failed workflow can be prepared again as a new request. Rerunning an existing run is deliberately rejected because its qualification identity has changed.

Runner subscription logins, backend GitHub token, signing credentials, protected environment policy, promotion authorization, first trusted packaged-Mac adoption and root updater setup must be verified operationally before enabling unattended preparation. Static tests and dry-run status are not evidence that these credentials or installations work.
