# Autonomous campaigns

An autonomous campaign turns an approved plan into several cards that run on their own, are merged into one campaign ("mother") branch, are validated together on a Coolify preview, and end with one final pull request to the base branch that a human reviews. The Orchestrator drives the whole journey through the local public MCP; the user never opens Atelier. Atelier owns the execution: plan versions, cards, the mother branch, merges, evidence, the final pull request and the report.

Scope of the first version: the VPS only, GitHub only, one executing campaign per repository. The Mac stays available for ordinary cards, and the final pull request is never merged automatically.

## Lifecycle

1. **Plan** — `submit_campaign_plan` stores a version: cards with their prerequisites (several allowed), a sub-budget and verifiable criteria, global criteria, ranked frozen attachments (absolute path and sha256 on the VPS), accepted assumptions, questions, exclusions, the token envelope and final reserve, the deadline, report and review times, the quota policy, the partial-delivery policy and the allowed external effects. Each criterion has `id`, `data`, `role`, `actions`, `observableResult` and `proofMethod`. A cycle, an unknown prerequisite, an incomplete criterion, a card asking to merge or to target the base branch, or inconsistent budgets or times are refused with their cause. Every change is a new version (`baseVersion` guards against stale edits).
2. **Readiness** — `check_campaign_readiness` lists every prerequisite with its cause: repository, protection of the base branch, rules of the mother branch (no required approval, no merge queue), CI on pull requests to the mother branch (absence must be accepted in the plan with `ciAbsenceAccepted`), the Dockerfile preview recipe, a free preview-broker slot, readable attachments, provider quota, the autonomous pilot and the `simplifier` / `argus-review` skills. A missing skill is a warning: internal guidance replaces it until it is installed.
3. **Skill install** — after the user clicks Install in the Orchestrator, `install_campaign_skill` copies the complete skill folder into the Claude and Codex skill roots of the service, either from the files the Orchestrator sends (copied from the other paired machine) or from skillzer at pinned commit `8f3ccad` (which has `argus-review` but not `simplifier`). A different installed version is never overwritten without the fingerprint the user chose after comparing (`replaceSha256`). Nothing is ever installed without that call.
4. **Approval** — `approve_campaign` freezes the current version, records the skill fingerprints and creates the campaign once; it refuses a stale version, an unanswered blocking question, an unaccepted assumption or a blocked readiness item. Replaying the same `requestId` returns the first result.
5. **Execution** — when the repository is free, readiness is checked again (including drift of the base branch since approval). The mother branch is created from the base, then one card per plan entry, each targeting the mother branch. A card starts only once all its prerequisites are merged into the mother; any other start is refused. Each card runs the ordinary pipeline (lightening pass, blocking review, checks) and the campaign merges its pull request into the mother itself, only after a clean review and only into the mother. A merge conflict gets one bounded resolution; afterwards the card and its descendants are blocked and independent cards continue. Questions the plan does not settle block the card for the report; nobody is asked during the run, and card notifications are silenced.
6. **Finalization** — when every card is merged, at the deadline, when the budget is spent, or when nothing can progress, merges into the mother stop and one final autonomous (Devin) card adopts the existing mother branch. It freezes the revision, applies the simplifier and argus-review guidance, runs the checks, validates the global criteria on a Coolify preview of that revision, and opens the pull request to the base branch (pull request only). An incomplete campaign opens a draft listing what is missing, or only produces the report, as the plan chose; with nothing merged, no pull request is opened. The preview is kept until the review time, then cleaned; a cleanup failure is reported.
7. **Report** — at the report time a single report is produced from persisted state and sent as the only notification: verdict (`unknown`, then `ready`, `partial`, `blocked`), activity, final pull request, preview, criteria with their proof on the exact revision, cards, decisions taken alone with the plan rule that allowed them, pending questions and consumption (tokens, sessions, quota pauses, skill fingerprints).

## Commands

- `pause_campaign` — no new start or merge; a merge already emitted finishes first, then sessions stop. Unavailable during a quota pause.
- `resume_campaign` — paused cards restart one per pass. After the deadline, a new `extension` (deadline and additional tokens) is mandatory; a reported campaign can be reopened the same way.
- `cancel_campaign` — ends the campaign; merges already in the mother, branches and work are kept and the report is produced.
- `get_campaign` — status, plan, versions, cards, report and the events after `cursor`; pass the returned cursor to read only new changes. `list_campaigns` lists them.

Every command takes a `requestId`; replays return the first result. A command naming a stale `version` is refused with the current one. URLs in responses carry no credentials, query string or fragment.

## Quota and capacity

A quota refusal (a rejected Claude rate-limit window, or a session error naming a usage limit) pauses the campaign: state is saved, sessions stop and the provider and estimated resume time are shown. When the plan allows it, the campaign resumes progressively once the observed quota is available again, before the deadline and while budget remains; unknown or stale quota counts as unavailable, and repeated refusals back off. No provider switch happens. Implementer admission follows the service memory (`KANBAN_MAX_IMPLEMENTERS`, `KANBAN_IMPLEMENTER_MEMORY_MB`, `KANBAN_MEMORY_RESERVE_MB`, `KANBAN_MIN_FREE_DISK_MB`; see [vps-install.md](vps-install.md)).

## Restart

Every remote effect is journaled before it is emitted. After a restart the engine re-reads the journal: a merge whose outcome is unknown is checked on GitHub before any retry, a started card is not started again, and a final card is created only once.
